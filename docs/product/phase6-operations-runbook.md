# PRODUCT運営Runbook — 販売・法務・保守

2026-10-18 / PRODUCT / 本番作業を承認する文書ではありません。
匿名ローカル検証の手順と、販売前に担当者が確認する運営手順を分けます。

## 運営の入口と日常確認

専用のPRODUCT運営者でログインし `#operator` を開く。園ADMINのアカウントを兼用しない。
毎営業日の開始時（担当・営業時間・休日対応は販売前に決定）に、申込一覧、問い合わせ受付、契約期限・停止状態、backup成功日時・監視通知を確認する。
画面には最新100件を表示する。大量受付時に古い未処理を埋没させない検索・ページングと担当割当は販売規模に応じたRC確認項目。受付番号で詳細APIへアクセスできるが、一般利用者へ技術操作を要求しない。

## 新規申込・園作成・管理者招待

1. 販売前チェックリストで規約・価格・個人情報・運用の承認があることを確認する。現在は未承認草案のため公開申込を受け付けない。
2. 申込一覧の園名・連絡先・希望プラン・受付番号を確認する。フォームの入力だけを本人認証として扱わない。
3. 既存の非公開連絡経路で、申込権限と最初の管理者本人・連絡先を確認する。不審な場合は園を作成しない。
4. 園作成欄に受付番号・申込と同じ園名/管理者名・新しい園コードとログインIDを入力し、本人確認欄をチェックする。運営者を園ADMINへ登録しない。
5. 作成後は申込とTenantが結び付く。重複処理は拒否される。初期契約は30日TRIAL。希望プランだけでは有料機能を開放しない。
6. 一回だけ表示される招待を本人へ安全に渡す。48時間以内に登録。再発行は旧招待を無効にする。招待本文をサポート記録や共有ログへ残さない。
7. 初回登録後、園管理者が既存SetupのHARD項目を完了する。未設定ならシフト作成へ進まない。職員名・勤務条件を他園からコピーしない。

## 契約変更・停止・再開・解約・再契約

- `#operator` の契約画面で対象Tenant ID、現在のプラン・期間を確認する。
- 支払・契約の確認根拠を別の承認済み経路で確認し、参照番号と変更理由を記録して有料契約を有効化する。本Phaseは実決済なし。
- 期間の開始/終了と上限を入力し保存。園側の契約表示とAPI実権限を確認する。契約情報不明は開放しない。
- 停止は理由を入れて運営が実施。園の業務APIは拒否、本人の問い合わせは継続可能。停止を解除するのは運営者だけ。
- 解約予約は期間末まで利用可能。終了時に業務機能を閉じるがデータは削除しない。
- ダウングレードで高度な既存条件が残る場合、勝手に削除・無視しない。契約状態とSetup警告を確認し園と調整。
- 再契約は本人と保持状況を確認したうえで新しい有効期間・確認番号を登録し、既存データとFeature Guardを照合する。
- 不用意なTenant削除API・自動期限削除は追加していない。

## 問い合わせ対応

1. 園利用者はログイン後「お問い合わせ」。停止中は「契約のご案内」内から送信できる。ログイン不能は公開サポート情報の既存連絡先を使う。
2. 氏名・健康情報・パスワード・招待情報を求めず、画面・日時・操作・結果を匿名で確認する。添付なし。送信成功と受付番号を確認する。失敗を受付成功として扱わない。
3. 運営はカテゴリ・受付番号・状態だけの一覧から必要な1件を開く。本文閲覧を監査に記録する。職員情報一覧を横断表示しない。
4. 状態は「受付済み→対応中→対応完了」。返信と状態は一つのtransactionで履歴に残る。送信者の追記は再受付に戻す。
5. 返信は同じ画面で確認。メール通知なし、即時回答保証なし。運営が画面を確認する運用が必要。
6. 同じTenantの管理者でも他職員の問い合わせ本文は見えない。運営者は必要な本文だけ扱う。本人以外の園への転記は禁止。
7. 1利用者につき1日10件、1件あたり100メッセージ、本文4000文字。超過時は再試行案内・新規受付。監査には本文を複製しない。
8. 旧ローカル保存を自動送信しない。利用者が必要な部分を匿名化して新たに送信する。過剰PIIが入った場合は閲覧・共有を最小化し、削除依頼の審査経路へ回す。

## 障害対応の共通手順

1. **検知**：監視、問い合わせ、backup失敗から発生日時と現象を記録。認証情報・本文・実職員名をPRODUCTログへ貼らない。
2. **一次確認**：正式URL、HTTP status、health/ready、release/build、ブラウザと時刻をREAD ONLYで確認。SSL検証やセキュリティを無効にしない。
3. **影響範囲**：全園か1園か、ADMIN/職員、ログイン/読み取り/更新、最初と最後の正常時刻、直前の変更を照合する。
4. **必要な停止**：誤った更新や境界事故が疑われる場合は新規操作を止める。承認済み権限で対象Tenantを停止し理由を記録。全体停止・基盤変更は責任者承認。DB障害時にアプリの停止設定変更ができると仮定しない。
5. **復旧**：原因と影響を明記し、隔離再現・修正・backup・review後に実施。手作業DB編集で症状を隠さない。
6. **確認**：認証・契約・Tenant境界・代表月次操作を確認。復旧時の古い契約が勝手に有効化されないことを確認。
7. **記録**：時系列、原因、変更SHA、影響範囲、承認者、復旧証拠、再発防止、未解決項目を残す。通知義務等はLEGAL REVIEW REQUIRED。

| 現象 | 一次確認 | 復旧確認 |
|---|---|---|
| ログイン不可 | HTTP、日時、User/Membershipの有効性・tokenVersion、契約表示。秘密を聞かない | 新しいログインと本人Tenant、他園拒否 |
| 生成不可 | Setup HARD、契約、対象月、ERROR、勤務条件。無理な割当で隠さない | 同じ匿名再現条件で生成・回答・再評価 |
| 契約異常 | Plan/状態/開始終了/上限/更新根拠。Fail Closedを解除しない | metadataと実APIの一致 |
| サービス停止 | Web/API health、reverse proxy、DB到達性、直前リリース | 各層healthと業務経路 |
| DB障害 | 接続・容量・backup成功時刻、書き込み停止の要否 | 新DBへ隔離復旧、整合性・契約・認証 |
| 誤操作 | 操作時刻、対象ID、監査、どこまで更新済みか | 該当園のみの訂正案と承認、他園影響なし |
| Tenant境界疑い | 当該アクセスを止め、対象ID/権限/ログを保全。本文拡散しない | 異常経路の否定テスト、影響園照合 |

## セキュリティ事故

認証情報漏えい・不正アクセス疑いは、影響TenantとUserの識別、既存token失効/アカウント停止・Tenant停止の必要性を確認する。secret本文をログに保存しない。証拠を保全して責任者へ連絡し、専門家と報告/本人通知の要否・期限を判断する。
復旧には、原因修正、必要な認証情報更新、権限見直し、負のTenantテスト、監査確認が必要。アプリ運営者の権限とインフラDB管理者権限を分け、DBアクセスは申請・限定時間・目的・記録を必要とする。アプリのisPlatformAdminだけでインフラ保護が済むとはしない。

## Backup / restore

既存 `ops/postgres-backup/backup.sh` / `restore-verify.sh` / `test-safety.sh` を再利用する。
対象はPostgreSQL全体（契約、User/Membership、招待、勤務、同意、問い合わせを含む）。コード・リリース・設定・鍵は別保全対象で、DB dumpには含まれない。
日次と重要変更前にbackup。既存の最低7世代は技術的な安全下限であり、PRODUCTの法的保持期間の決定ではない。RPO/RTO、暗号化別置き保管、保管地域、鍵管理、監視通知先は販売前に責任者が承認する。新しい保管サービスを契約していない。

1. 対象環境と成功時刻・容量・private権限を確認する。資格情報は600のPGPASSFILE等で管理し、表示しない。
2. SHA256とarchive一覧を検証。失敗なら更新作業を停止。
3. localhostの新しいrestore_verify/test DBへ復旧する。既存DBへ上書きしない。必要なDBを名前で明示し、本番を復旧先にしない。
4. migration完了、Tenant境界、主要件数・月次digestを確認。
5. 新しい契約/同意/問い合わせ/監査/メンバーシップについて元データとの一致を確認。
6. 復旧DBでログイン、他園拒否、本人データを確認。古いbackupからの契約期限・停止状態の巻き戻りを別台帳と照合する。
7. 本番切替は別承認。試験スクリプトは切替しない。

Tenant JSON v3は可搬export/検証/previewであり、完全復旧ではない。Subscriptionや全設定・新申込/問い合わせ等を網羅しない。Tenant単位の自動restoreは未実装。1園だけの復旧は全DBを隔離復旧し、関連データ・他園影響を精査した修復案をレビューする。全DBをそのまま本番へ戻して他園の新しい更新を失わせない。
Phase 6の匿名試験は既存dump/restoreスクリプトを使用し、原本一致・ログイン・境界を確認する。本番backupの実効性や別地域災害復旧を試したことにはしない。

## 保持・削除 — LEGAL / BUSINESS DECISION REQUIRED

| 対象 | 現行 | 選択肢・影響 |
|---|---|---|
| 解約後業務データ | 契約終了で非公開、即削除なし | 期間後削除/匿名化/返却。本人確認と他園影響照合が必要 |
| 申込と同意 | 削除APIなし。関連Tenant削除はRESTRICT | 証跡保持と不要申込削除の期間を分ける |
| 問い合わせ | 本文/返信/状態をDB保存。Tenant削除時cascade | 期限後本文匿名化と受付監査保持の分離を検討 |
| 監査 | DB内、Tenant削除でcascadeされ得る | 法務上の証跡要件・アクセス・不変保管を別途決定 |
| backup | 世代保全、解約直後にdump内を個別消去しない | 世代満了/暗号鍵管理/復旧時の削除済みデータ再出現防止台帳 |
| 削除依頼 | 自動処理なし | 依頼者本人/権限確認→対象一覧→保持義務確認→承認→限定実施→確認記録 |

期限・保持期間をコードに固定していない。削除操作や本番データ変更は本Phaseでは行わない。

## 旧契約の互換性と適用前手順

旧契約でtrialStartedAt/trialEndsAt、または有料契約のcurrentPeriodStartedAt/currentPeriodEndsAtがnull・逆転・未来開始・不正値、未知状態・上限異常の場合、現在のFail Closedは業務機能を拒否する。契約metadataと本人問い合わせは残る。

1. PRODUCT適用対象の契約一覧を、承認されたREAD ONLY監査で照合する。今回MUSUBI/Pilot実データは監査・変更していないため影響件数は不明。
2. Plan/状態/期間/停止理由/上限/確認済み契約参照を分類し、欠落を「有効」と推定しない。
3. 契約原本・本人確認・管理責任者の承認で正しい値を決める。全園STANDARD化や適当な将来日付で回避しない。
4. 匿名化した不整合ケースで修正手順とFail Closedを検証。既存Migrationは改変しない。
5. 実適用は別承認、直前backup、現状snapshot、対象Tenantを限定した既存運営API、監査記録、変更後API/UI照合の順。失敗時は安全側の停止を維持。
6. PilotへPRODUCT branchを丸ごとmergeしない。互換性と契約条件を確認した変更だけを独立レビューする。
